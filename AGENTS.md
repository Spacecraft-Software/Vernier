# Vernier — agent context

Vernier (`vnr`) is a Rust display configurator replacing wdisplays (Wayland)
and ARandR (X11). Spacecraft Software project; maintainer Mohamed Hammad.

- **Assurance category:** C (Steelbore Standard §19). A bad configuration is
  visible and recoverable: every apply is followed by confirm-or-revert.
- **Plan and progress:** `PLAN.md` (§17.5 format). Tick an item only when it
  is implemented and verified.
- **License:** GPL-3.0-or-later. Every source file carries the two-line SPDX
  header. `unsafe` is forbidden.

## Layout

| Crate | Role |
|---|---|
| `crates/vnr-core` | Model, geometry, validation, profiles, exporters, `Backend` trait. No I/O. |
| `crates/vnr-wlr` | wlr-output-management v4 + COSMIC extension (vendored XML in `protocols/`). |
| `crates/vnr-x11` | X11 `RandR` through `x11rb`'s pure-Rust connection. `state.rs` holds the pure snapshot/plan logic. |
| `crates/vnr-kde` | KDE Plasma through `kde_output_device_v2` / `kde_output_management_v2`, compiled from the vendored XML in `protocols/` (keep it as new as current KWin's, or unknown events abort the connection). `plan.rs` holds output priorities. |
| `crates/vnr-mutter` | GNOME through `org.gnome.Mutter.DisplayConfig` over `zbus`. `state.rs` holds the pure logical-monitor translation, including physical-layout reflow. |
| `crates/vnr-backends` | Run-time detection, `open()`, and the `fixture` backend (`VNR_FIXTURE=<file.json>`). |
| `crates/vnr-config` | The Nickel configuration file (`config.ncl`) and the editor's key map; toolkit-independent. |
| `crates/vnr-theme` | Steelbore tokens and §11.6 theme resolution, shared by CLI colors and the editor. `assets/steelbore.toml` is the canonical palette, never edited by hand. |
| `crates/vnr-gui` | iced editor. `overlay.rs` draws the screen labels and `preview.rs` captures screen contents (`ext-image-copy-capture-v1`, else `wlr-screencopy`), each on its own thread and Wayland connection. |
| `crates/vnr` | The `vnr` binary: CLI Standard v1.1 grammar, output modes, errors, schema. |

## Commands

```nushell
cargo fmt --all
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace --locked
cargo deny --locked check             # licenses, sources, advisories (deny.toml)
                                      # advisory ignores live in deny.toml and .cargo/audit.toml
cargo audit
cargo run -p vnr -- gui --demo        # editor on a sample layout, no display changes
make info html pdf                    # the manual (doc/vernier.texi) into doc/build/
python3 scripts/guix-crates.py        # after every Cargo.lock change; CI checks it
```

The Texinfo manual is user documentation: change it in the same pull request
as any behaviour, option or exit code it describes. It builds with zero
warnings.

CLI tests (`crates/vnr/tests/cli.rs`) run the real binary against the fixture
backend, so they need no display server. Each display backend also has an
end-to-end test against a real headless server (sway, the Xorg dummy driver,
`KWin`, Mutter), ignored by default. One script starts the server in a
private `XDG_RUNTIME_DIR`, runs the test and stops it; CI runs all four, and
sway once more from nixpkgs for the newer capture protocol:

```nushell
sh scripts/test-servers.sh sway        # or kwin, mutter; sway also runs the screen-contents test
with-env { SUDO: sudo } { sh scripts/test-servers.sh xorg }   # Xorg needs root
```

Changes land through a pull request that is squash-merged on GitHub, which
signs the merge commit; agents never sign commits themselves.

## CLI invariants (Spacecraft CLI Standard v1.1)

- Grammar is `vnr <noun> <verb>`. A new leaf command needs a `Spec` entry in
  `crates/vnr/src/spec.rs` (two or more examples, one with `--json`); a unit
  test fails otherwise.
- stdout carries data only, through `Out::emit`. Diagnostics go through
  `Out::diag` with a code listed in `spec::DIAGNOSTICS`; errors are
  `AppError` values returned to `main`, never printed by commands.
- Every error hint is a runnable command. New error codes go in
  `error::ErrorCode` with a documented exit code.
- Argument structs derive `JsonSchema`; their doc comments are both the
  `--help` text and the schema descriptions.
- Path arguments go through `validate::Roots::check`; commands that change
  state or write files honor `--dry-run` and need `--yes` to overwrite.
  The one exception is `--persist`: it replaces only a file whose first line
  marks it as generated by Vernier (`export::is_generated`), with or without
  `--yes`, and never niri's `config.kdl`.
- Agent detection is presence-based (`AI_AGENT=claude-code_…` counts).

## Requirements (Steelbore Standard §20, Category C)

The requirement set lives here and nowhere else; `PRD.md` holds the needs
and scope and points here. Identifiers are permanent: a withdrawn
requirement keeps its row, struck through, and its number is never reused.
Needs (`NEED-`) are listed in `README.md`. Status is one of `draft`,
`baselined`, `implemented`, `verified` or `withdrawn`; only `verified` counts
toward the PLAN figures, and only for `mandatory` and `expected` rows.
Prefix every identifier with `VNR-SRS-` when citing it outside this table.

## Conventions

- Backends are synchronous and short-lived; callers open one per operation.
  Never cache a wlr serial across operations.
- Every apply path must keep the previous `Layout` and offer revert.
- Colors only through `theme::Steelbore` tokens; no hex literals in UI code.
- Library crates use canonical error structs (`BackendError`, `ProfileError`);
  only `vnr-gui` uses `anyhow`; `vnr` uses `AppError`.
- Commits on `main` are signed: by the maintainer, or by GitHub when it
  squash-merges a pull request. Pushes go over HTTPS (Steelbore Standard
  §6.3–§6.4). Agents never handle signing keys.
